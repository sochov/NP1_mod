# QMMF停止と純正カメラ利用側の依存関係

## 確認した再起動経路

2026-11-12の調査で、利用者がWebから `qmmf-server.service` を終了した後、本体が再起動した3件を確認した。調査側から純正サービスの停止・開始・再起動や本体再起動を追加実行していない。

通常の前boot journalは再起動後に残っていなかったが、純正のcore保存処理が異常発生前後のjournalと、異常終了プロセスのcmdlineを保存していた。これらを読取りで照合した。数値PID・実機識別子・core・生ログは公開しない。

以下の時刻はすべて2026-11-11 UTC。JSTでは翌12日01時台にあたる。

| QMMF停止開始 | QMMF停止完了 | 利用側の異常・core処理開始 |
|---|---|---|
| 16:01:18.127 | 16:01:18.211 | 16:01:26.095〜26.129 |
| 16:02:46.697 | 16:02:46.782 | 16:02:54.519〜54.544 |
| 16:04:33.318 | 16:04:33.407 | 16:04:41.131〜41.161 |

3件とも次の順で一致した。

1. Web操作によってQMMFが inactive になる。操作直後の単体読戻しは成功していた。
2. 約8秒後、`NEventWatcherAV` 内で `vin_qmmfsrc` を PLAYING のまま解放しようとする警告が出る。
3. 同プロセスに `qmmfsrc_init` の `context != NULL` assertion失敗が記録される。
4. `NPVINDeviceCont` スレッドの SIGSEGV（signal 11）をcore処理が捕捉する。保存cmdlineは3件とも `/usr/local/bin/NEventWatcherAV`。
5. 純正corefilterが再起動直前の情報保存まで進む。

`core_pattern` は純正corefilterを指す。取得済み純正corefilterには、保存したcmdlineが `/usr/local/bin/` 配下の場合、純正プロセス群へTERMを送り `reboot -f` する処理がある。この条件と今回のcmdline・実測時系列が一致する。QMMFのunit自身に再起動命令があるという説明ではなく、QMMFを利用中の純正処理が異常終了し、本体の異常復旧経路に入ったと判断する。

`signalhandler_app.sh` / `signalhandler_lib.sh` は別の終了後処理であり、TERMは本体再起動の対象から除外する。一方、KILL等では本体を再起動する。今回のSIGSEGVはkernelのcorefilter経路であり、「QMMFへの通常のTERMだから本体も再起動しない」とは保証できない。

DriveRecにはカメラ異常時に `NSystem::Reset` へ進む別の静的経路もあるが、今回3件の保存ログでは、それを直接の実行原因とする証拠は見つかっていない。確認できた NEventWatcherAV / corefilter の経路と混同しない。

## systemdの依存関係だけでは足りない理由

`--job-mode=ignore-dependencies` は別unitへのsystemdジョブ伝播を抑える。既にQMMFを利用しているコードが、QMMF停止後も動き続けることや、利用側の不正な再初期化を防ぐ機能ではない。今回の停止直後の確認は成功し、その約8秒後に利用側が落ちている。対象unitの短時間の状態確認だけで、周辺サービスを含む操作成功とは扱わない。

QMMFは通常の補助サービスと異なり、純正カメラ処理の基盤として扱う。単独停止・再起動をそのまま許可し、純正の異常復旧を無効にして回避する実装は採らない。

## 固定の操作ガード

カメラ利用側の静的解析から、次の5アプリを保護対象とする。

| unit | 根拠と範囲 |
|---|---|
| `app-@DriveRec.service` | 録画・カメラ利用 |
| `app-@ImageRecog.service` | 認識・画像出力のためのカメラ利用 |
| `app-@RemoteMonitoring.service` | リモート監視のカメラ利用 |
| `app-@VirtualPassenger.service` | 対話機能のカメラ利用 |
| `app-@System.service` | カメラのSceneMode等の設定要求。映像取得専用の利用側とは区別するが、稼働中の設定要求も保護する |

固定API IDに対して以下を適用する。任意のunitを操作対象や依存先として受け取らない。

| 操作 | 必要条件 |
|---|---|
| QMMFの停止・再起動 | 上記5アプリと `NEventWatcherAV` がすべて停止済み、MainPID 0、進行中Jobなし |
| NEventWatcherAVの停止・再起動 | 上記5アプリがすべて停止済み、MainPID 0、進行中Jobなし |
| NEventWatcherAVの開始 | QMMFが稼働している |
| 上記カメラ利用アプリの開始 | QMMFとNEventWatcherAVが稼働している |

状態不明・読取り失敗・移行中は操作可能と推測しない。GETの操作可否・理由表示に加え、POSTの実行直前にも改めて依存状態を取得して拒否する。再起動には停止が含まれるため、停止と同じ保護を適用する。

「カメラ関連を一括停止する」機能は今回実装しない。アプリ → AV → QMMFの順は候補になるが、5アプリを停止した場合の別機能への影響、終了待ち、原状復帰、録画・ライブ映像の復帰まで実機検証してから扱う。利用者が選んでいない複数サービスを自動で停止して操作を成立させない。

Web以外からの直接操作や純正側の状態遷移まで、このガードで完全に防止できるとは主張しない。純正のunit・バイナリ・corefilter・異常復旧方針は変更しない。

## 検証範囲

- 原因確認は、既に発生した3件の保存coreメタデータ・保存journal・純正スクリプトの読取りで行った。原因再現のための追加停止はしていない。
- hostテストでは、保護対象が稼働中・不明・進行中Jobを持つ場合の拒否、停止済みの場合の条件、GET可否とPOST再検査の一致を検証する。
- 修正後の実機確認はGETだけで行い、カメラ利用中のQMMF/AVの停止・再起動可否がfalseで理由が表示され、QMMF・利用側のPID/状態と本体起動IDが不変であることを確認した。POST直前の再照会・拒否と操作コマンドが0回であることはhostテストで検証した。新たなQMMF停止要求や異常再現は実機で実行していない。
- 固定サービスIDとstart/stop/restartを、brokerへ送る前に非rootの永続監査ログへrequestedとして保存する。応答後のaccepted/rejectedと組にする。個体情報や任意のcommand文字列は記録しない。
- 以前のOpening個別操作の合格は、QMMF停止時の依存関係まで検証したものではない。今回の実測で得た制約を追加する。
- 起動直後にライブ出力と録画が戻ったことと、元の停止操作が安全だったことも区別する。

個別操作とsingleton lockの詳細は [stock-services.md](stock-services.md) を参照。
