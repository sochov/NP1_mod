# ナンバー認識の遅延内訳とPP-OCRv6の高速化

2026-11-20。起点は `ca6a6dd`。5秒台の計測はPP-OCRv6を含む同梱モデルを使った再生試験。実機に導入済みの旧モデル構成にはPP-OCRv6の設定がない。

## 遅延の内訳

NP1で同梱モデルのCPU経路を使い、同じ合成フレーム3枚を再生した。陽性フレームの中央値は5,356 ms。候補は1枚で、PP-OCRv6を1候補につき10回実行した。ONNXの実行が5,048 ms、画像切り出しと入力作成が4.5 ms、検出が234 ms、TFLiteの読取り器が45 msだった。PP-OCRv6は地名・かな・一連番号を切り出して読み、条件に応じて別の切り出しでも再照合する。

## 実装と検証

- 既存のPP-OCRv6をONNX opset 13に変換し、畳み込み62個をQLinearConvに量子化した。入力活性はUINT8、重みはチャネル別INT8。校正には既存のプレート描画ツールによる合成画像の地名・かな・番号・文脈切り出し96点を使った。校正入力は評価フレームと別に作成し、出力側の分類・CTC確率・照合条件は既存の浮動小数点経路を使う。
- ビルドは、従来のONNXと量子化ONNXの両方を同梱する。量子化版のファイルが無い場合や起動・推論に失敗した場合は従来のモデルを使う。推論中の切替時は、そのプレートの読取りを従来モデルでやり直す。`NCC_PLATE_PPOCR=original` で従来モデルの測定ができる。
- 補助のTFLiteモデルは結果を使う分岐に入ったときに呼ぶ。地名候補の不一致が確定した場合は残りの切り出しを省く。
- 取得間隔が処理時間と重複して加算されていた状態を修正した。既定500 msの取得間隔には処理時間を含め、遅延時は最新フレームを読み直す。

CPU 150%、メモリ384 MiBの一時スコープで、同じエンジンと入力を使って従来モデルと量子化版を比較した。録画14枚と合成3枚のうち陽性16枚を集計した。17枚すべてで地名・分類番号・かな・一連番号と、既定の記録対象・即時記録の判定が一致した。

| 実機での計測 | 従来モデル | 量子化版 |
| --- | ---: | ---: |
| 陽性フレームの中央値 | 3,456 ms | 1,694 ms |
| 全フレームの最大値 | 7,291 ms | 3,196 ms |
| 陽性フレームのONNX実行時間の中央値 | 3,171 ms | 1,350 ms |
| 陽性フレームのONNX実行回数の中央値 | 9回 | 9回 |

実機のAdrenoキャッシュを再利用し、GPU検出、GPUによるTFLite読取り、CPUによるINT8のPP-OCRv6を組み合わせた代表フレーム1枚も読取りに成功した。全体1,901 msのうち、検出は129 ms、TFLite読取りは23 ms、PP-OCRv6の推論は1,725 msだった。初期調査で従来の浮動小数点モデルとGPUを併用した計測は実機の再起動で中断した。再起動の原因は特定できず、その後の比較では純正サービスの稼働と録画継続を確認した。

## 検証と適用方法

```sh
python tools/device/bench-plate-engine.py --serial SERIAL --engine artifacts/plate/plate-engine-aarch64 --baseline artifacts/plate/plate-engine-aarch64 --baseline-models BASELINE_MODEL_DIR --frames REPLAY.nv12 --frames-only --cpu-only --service-limits --report tmp/plate-ocr-profile.json
python tools/device/deploy-plate-engine.py --serial SERIAL --worker artifacts/ncc/bin/ncc
```

比較スクリプトは、コードとモデルを一時領域に置き、検出・TFLite・切り出し・ONNXの実行時間、読取り文字列、既定の記録しきい値の一致件数だけを報告する。NP1への適用は、既設モデルを使う構成に対し認識プロセス専用のNCCバイナリを配置する。配備処理は認識エンジン、認識ユニット、以前の専用バイナリを所有者領域の復旧ディレクトリに保存する。復旧には配備時に表示されたディレクトリを指定し、同じツールの `--rollback` を使う。

`bench-plate-engine.py --compress-frames` は入力フレームを圧縮して一時領域に置き、実機で逐次展開する。表示する認識時間はエンジン内部の値で、撮影・転送・展開の所要時間は含まない。比較する両ケースに同じ入力を渡し、試験後に一時ファイルを削除する。

`--service-limits --frames-in-ram` は空きメモリを確認したうえで、入力を本体の `/run` に置く。既存認識との並行負荷を切り分ける場合は `--isolate-owner-plate` を指定できる。キャッシュ準備後に所有者用の認識センサーを一時停止し、試験後に復帰する。接続が切れた場合に備え、復帰用のタイマーを本体に設定する。`--sensor-paced` は毎秒8枚で供給する録画から実際に処理できたフレームと、対象番号を保存できたかを記録する。

モデルも更新するときは `deploy-plate-engine.py --models` に配布用のモデルディレクトリを指定する。マニフェストに記載された全モデルをハッシュで検証し、実機で同じ内容と権限のファイルはハードリンクで再利用する。更新前のモデルディレクトリは復旧用に保持する。`--prepare-detector` ではGPUキャッシュを作り、実際の推論を1回行ってから適用する。

配備前の認識速度の表示は1.55 fps。配備後はGPUによる検出と読取りで約2.0 fpsに達し、処理済みフレームの時刻が進み続けた。稼働中の認識バイナリ、既設モデル、共有NCCバイナリをハッシュで照合した。純正5サービスは配備前後で状態と起動IDが一致し、前方と車内のJPEG取得、SD録画のRange読み出し、実機のナンバー画面のテスト2件に合格した。
