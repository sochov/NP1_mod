# ナンバー認識と発話

前方カメラの映像からナンバーを読み取り、場所と一緒に記録します。条件に合ったナンバーは地図で目立たせ、画像を保存し、本体のスピーカーで読み上げます。DRIVE RECORDERの「ナンバー」画面と、システム › LED / 音声の「音声合成（VOICEVOX API）」で設定します。

「ナンバー → 条件と設定」で「条件に関係なく、ナンバー検出時にLEDを光らせる」をオンにすると、新しく記録した車両ごとに白く点灯します。同じ車両の連続した検出は既存の記録にまとまります。条件ごとのLED通知があるときは、その色と点灯方法が優先されます。初期状態ではこの設定はオフです。

**開発版の機能です。** 精度・対象・制限を理解したうえで利用してください。認識した他の車のナンバーは個人に結び付き得る情報です。保存や共有の扱いは各自の責任で判断してください。

## LED通知

「条件と設定」の各条件で「LED通知」を設定できます。単色は色・明るさと「点灯」「ゆっくり点滅」「流れる光」を選び、レインボーは色が連続して変わります。発話中と終了後2秒間光り、発話を使わない条件は2秒間光ります。「本体で試聴」でも同じLED通知が動作します。発話なしの条件は「LEDを試す」で確認できます。

通知が終わると消灯します。画面連動中はその映像の表示へ戻ります。LED通知の初期値は「なし」です。システムの前面LEDも一時点灯が既定で、「点灯」「消灯」で試せます。

## 仕組み

| 段階 | 内容 |
| --- | --- |
| 認識 | 認識サービス（`np1-control-plate.service`）が、純正の前方カメラ出力（1920×1080）を既定で毎秒4フレームを目標に取得します。検出したプレートを各フレームでOCRし、地名・分類番号・ひらがな・一連番号を読み取ります。複数のプレートが写ったときは、それぞれの検出枠を追跡します |
| 位置 | 検出した秒の位置を、純正が毎秒更新する位置（ダッシュボードの地図と同じもの。動いているか直近10分のNMEA測位と矛盾しない場合だけ採用）から付けます。付かなかった記録は、録画の区切り（約3分ごと）でSDカードにNMEAが書き出された後、検出時刻の前後3秒以内の測位で2分ごとに補います（過去30日分、SDカードにNMEAが残っている範囲）。どちらでも測位が見つからない場合は「位置なし」のままで、地図には表示しません。過去の記録は `tools/plate/fill_locations.py` で、保存済みの走行記録から補えます。前後の既知の位置から時刻比例で推定した位置は「位置推定」と表示し、地図では点線の印にして、誤差の目安（50m〜1km）を添えます |
| 記録 | 1〜4桁の一連番号を同じプレートから2回以上読めたときに記録します。地名・分類番号・ひらがなは空欄でも記録できます。短時間だけ写った場合は、他の一連番号の読みと競合せず、幅50px以上で信頼度0.75以上、または幅45〜49pxで0.80以上なら1回の読みで記録できます（初期値）。最初と最後の検出時刻と検出フレーム数を保存します |
| 発話 | 条件を保存したときに、読み上げる文をWEB版VOICEVOX APIで音声にして本体に保存します。検知したら保存済みの音声をつなげて、本体のスピーカーで再生します |
| 共有（任意） | 「共有」でNumberShare APIを設定して有効にした場合だけ、確定した検知の構造化ナンバー・検知日時・実測位置を端末内キューから送信します。画像と推定位置は送信しません |

認識はすべて本体内で行います。通常は記録・画像・位置を本体（`/overlay/owner-apps/np1-control/state/plate/`）にだけ保存します。「共有」でNumberShareを明示的に設定して有効にした場合だけ、下記の情報を外部APIへ送信します。

## NumberShareへの共有

「共有」タブでは、利用者が用意したAPIエンドポイントと認証キーを設定できます。初期状態は未設定・停止です。

- 検知が確定すると、送信前にUUID v4のイベントIDと本文を `state/numbershare/queue.json` へ保存します。API成功まで同じイベントID・同じ本文を再送するため、タイムアウト後も重複登録しません。
- 接続失敗、HTTP 429、5xxは指数バックオフで自動再送します。認証失敗、入力不正、競合、削除済みイベントなどは無限再送せず「確認が必要」とし、設定変更または画面の「再送」で再開できます。
- 送信するのは構造化ナンバー、最初の検知日時、実測できた緯度・経度・精度です。画像、録画、認識信頼度、ローカル条件名、前後の走行記録から推定した位置は送信しません。
- 認証キーは `state/numbershare/config.json`（0600）へ保存し、ブラウザーへ返さず、ログにも記録しません。HTTPS以外のエンドポイントは受け付けず、証明書検証を無効にできません。
- 共有履歴の「自分」は、端末内キューに残るイベントIDとの一致で判定します。APIが他の利用者のIDや端末IDを公開することには依存しません。地図と一覧では自分をオレンジ、他の利用者を青で表示し、表示範囲を絞れます。
- 保存済み履歴は開始日・終了日を指定して後からアップロードできます。期間内の全ローカル記録を対象にし、同じ記録は既存のイベントIDを維持して重複送信しません。
- API履歴の同期は100件単位のカーソルを最終ページまでたどり、固定件数で打ち切りません。
- APIの検知履歴はナンバー・照合状態で検索でき、登録車両は一連指定番号・地域／コメント・カテゴリで検索できます。

認証キーや復旧コードをGit管理下の設定ファイル、作業記録、ログへ貼り付けないでください。接続情報は画面から入力し、ソースコードには既定値を持たせていません。

## 使い始める

1. ナンバー画面の「条件と設定」で「ナンバーの記録を有効にする」をオンにして保存します。初期状態ではオフで、オフの間は認識処理も停止しています。
2. 「状態」タブで認識プロセスが「認識中」になっていることを確認します。
3. 走行すると「記録」タブの一覧と地図に増えていきます。記録を選ぶと、最初から最後の検出時刻に重なる自車の走行軌跡が緑の線で表示されます。白丸が始点、緑の丸が終点です。GPS記録の空白は線が途切れます。
4. 一覧の「録画を再生」で、その車を読んだ前後（最初の検出の10秒前から最後の検出の10秒後まで、最長3分）の前方カメラの録画を、画面を移らずに再生します。録画が上書き済み・未確定の場合はその旨を表示します。「ドラレコ再生で開く」で、同じ時刻からドラレコ再生画面を開けます。

## 条件

条件は100件まで登録できます。指定した項目がすべて一致したナンバーを「条件に合致」として扱います。空欄の項目は問いません。

| 項目 | 指定方法 |
| --- | --- |
| 地名 | 完全一致（例: 相模） |
| 分類番号 | 数字と英字、`*`は任意の1文字（例: `3**`） |
| ひらがな | 1文字（カタカナで入力してもひらがなとして扱います） |
| 番号 | 一連指定番号の数字、`*`は任意の1文字（例: `12**`） |

認識できなかった項目は条件を満たしません。たとえば地名を条件にすると、地名を読めなかった記録は合致しません。条件に合致した記録は、地図ではオレンジの大きな点で最前面に表示し、一覧では条件名を付けて強調します。「画像を保存する」をオンにすると、検出したときの前方映像を検出枠付きで保存します。

## 読み上げ

条件の「本体で発話する」をオンにすると、「メッセージ → 定型文 → ナンバー」の順に読み上げます。

> メッセージに続いて、検知した地名・分類番号・かな・一連番号を読み上げます。

- **メッセージ**: 条件ごとの文（60文字まで）。文字で入力するか、音声ファイル（mp3・wavなど、30秒以内）をアップロードします。音声ファイルはブラウザーで変換してから本体へ送ります。
- **定型文**: 全条件で共通（初期値「番号を検知しました。」）。
- **ナンバー**: 検知した読み。読めなかった項目は読みません。番号は2桁ずつ（25→にじゅうご、05→まるごー）、分類番号は1桁ずつ読みます。
- **声と音量**: 「条件と設定」の「発話」で選びます。初期値はずんだもん（あまあま）です。音量は読み上げの再生音量だけを変え、本体の音量設定は変えません。

条件を保存すると、その条件の音声を生成します。地名・ひらがな・数字などナンバーを読むための部品（約300個）は、声を選んだときに1回だけ生成します。生成中・完了・失敗は条件ごとに表示します。保存済みの条件は「この画面で聴く」でブラウザーから、「本体で試聴」で本体のスピーカーから確認できます。

番号まですべて指定した条件（`*`なし）は、ナンバーまで含めた全文を1つの音声として生成するため、より自然に読み上げます。それ以外は、メッセージと定型文の音声に部品の音声をつなげます。

1台につき読み上げるのは1回、最初に合致した発話条件の分だけです。記録の「発話済み」は、本体での再生が完了したときだけ付きます。VOICEVOX APIが未設定のときは「発話できず（未設定）」になります。

### VOICEVOX APIの設定

読み上げには [WEB版VOICEVOX API](https://voicevox.su-shiki.com/su-shikiapis/) のAPIキーが必要です。

1. [su-shiki.com/api](https://su-shiki.com/api/) でAPIキーを発行します。
2. システム › LED / 音声の「音声合成（VOICEVOX API）」にキーを入力して保存します。エンドポイントは初期値（`https://deprecatedapis.tts.quest`）のままで使えます。互換APIを使う場合だけ変更してください。
3. 「接続を確認」で残りポイントを確認できます。

キーは本体にだけ保存し、画面にもAPIの応答にも表示しません。APIへ送るのは、条件のメッセージ・定型文・番号まで指定した条件の読み・ナンバーを読むための部品だけです。走行中に検知した他の車のナンバーは送信しません。

APIには1日のポイント上限と、短時間の利用制限があります。部品の生成は約1.5秒間隔で行い、制限に当たると自動で待ってから再開します。生成した音声のクレジット（例: VOICEVOX:ずんだもん）は画面に表示します。生成した音声を本体の外で利用する場合は、[VOICEVOXと各キャラクターの利用規約](https://voicevox.hiroshiba.jp/term/) に従ってください。

## 精度と対象

連続フレーム追跡は、同時検出、誤読の訂正、読めないフレームを含む検出期間、日付をまたぐ表示を自動テストで確認しました。実際のカメラ出力を用いた3系列のローカル再生では3件を追跡し、うち2件で複数回のOCRが一致しました。代表画像の取得も確認しました。

以下は低解像度用OCRを更新したときの評価です。学習に使っていないNP1本体の走行映像と別機種2台のドラレコ映像を使用し、164台を人手で確認しました。追跡導入前のエンジンをコンテナ内のCPUで実行し、初期記録条件で比較しました。

| 記録の正答率 | 更新前（r2・旧シリアル読取り器） | 更新後（r4・plate-v2シリアル読取り器） |
| --- | ---: | ---: |
| 全体 | 86.1%（誤22・車122台） | 93.7%（誤9・車120台） |
| camA（昼） | 94.0% | 96.2% |
| camB（夜） | 84.4% | 93.1% |
| np1（夜中心） | 72.1% | 88.6% |

r4は判読できない幅では出力しない学習と重み付けにより、小さいナンバーの地名偏りと誤答を抑えています。走行映像の幅70px以上では千葉系の出力割合がr3の7.5%からr4の2.6%になりました。評価キットでは判読不能な1台に日光の出力が残ります。QCS610実機では全項目一致が開発分割で2〜6ポイント、選定に使っていないテスト分割で2〜3ポイント上がり、平均処理時間は約70ms増えました。実機のかな読取りにはPC評価との差があります。誤記録の減少は、bce9353で差し替えられたシリアル読取り器をplate-v2に戻したことによるもので、r3とr4では同じです。詳細な条件と残る課題は [評価まとめ](plate-lowres-evaluation.md) を参照してください。

- 対象にしやすいのは、前を走る車、信号待ちの車、駐車中の車、交差点でゆっくり動く車です。
- 夜間に遠く・小さく写るナンバー、強い逆光、事業用（緑）ナンバーは苦手です。写り幅45px未満では1回では記録しません。
- 幅40px未満の読みは、複数回一致した場合も信頼度0.78以上が必要です。幅160px以上で一連番号だけ読めたときは、標識などの誤認識を減らすために複数フレームの一致を求めます。
- 1回だけの記録を減らしたい場合は、設定の「1回で記録する信頼度」を上げてください（1で無効）。

## 設計の概要

- **2段構成**。検出器（MobileNetV2＋FPN、int8）が前方映像の中央下寄りの範囲（ROI）からナンバーを探します。読取り器は元の解像度からプレートを切り出し、地名・分類番号・ひらがな・一連番号を読みます。同梱のモデル構成では、かな・分類番号の専用モデルとPP-OCRv6も使って結果を照合します。
- **連続フレームの追跡**。枠の重なり、中心位置、面積比、直前の移動から、検出枠と追跡中のプレートを一対一で対応付けます。重なった検出枠は既存の追跡との対応を確認してから整理します。別々の追跡と対応する枠と、高信頼で異なる番号を読んだ枠を保持します。既存の追跡に対応した高信頼の枠と縦方向に重なり、未対応で読みが弱い枠は、重なりと中心の位置から重複を確認します。画面外側へ急速に移動する枠も、移動方向と大きさが整合する場合は候補に加えます。4フレーム以上追跡し、一連番号を2回以上支持した車両では、0.35秒以内の見失いを移動速度から補い、位置の予測と大きさが整合する枠を対応候補に加えます。数字が1桁食い違う場合は、読みの信頼度と地名などの一致を確認します。OCRが読めなかったフレームも、枠が対応していれば検出期間と回数に含めます。枠の対応が切れた後も、一連番号が完全一致し、位置・大きさの変化が妥当な候補が1つに絞れれば同じ記録にまとめます。同じ4桁を手前の追跡で3回以上読んだ場合、0.4秒以内の再出現は推定した速度から位置を予測して判断します。5秒を超える間隔（最大16秒）や補助項目が複数食い違う場合は、前後の枠と確読した枠の位置・大きさを比べ、複数回の一致を求めます。間隔が7秒以下で、前後とも3フレーム以上にわたり枠が検出され、枠がほとんど動かず、高信頼の4桁が一致する場合も再結合の候補にします。
- **OCR結果の選択**。追跡期間全体の一連番号の候補を最大24種類まで集計し、読みの信頼度、写り幅、検出スコアで票を重み付けします。画面の外にはみ出した枠の読みは投票に含めません。細長い枠や幅100 px以上で検出スコアが0.30未満の枠は、採用前にもう1フレームの読みを求めます。幅35 px未満では3フレームの支持が必要です。候補の票が拮抗するときは確定を保留します。地名・分類番号・ひらがなは、同じ番号を読んだ直近の結果を優先し、空欄は過去の同じ番号の読みで補います。一連番号を3回以上かつ過半数の読みで支持した場合は追跡中に記録し、その後は約2秒ごとと追跡終了時に同じ記録を更新します。短い追跡は終了時に記録条件を評価します。
- **短い追跡の見失い**。検出がまだ2フレーム以下で、2フレーム以上かつ0.5秒超の空白があった場合は、枠の位置がほぼ同じか、高信頼の一連番号が一致する場合に限り追跡を続けます。
- **短い重複の統合**。追加OCRを使う構成では、同じプレートに別の枠が立って追跡が分かれた場合も、最大175 msの重なり、同じ4桁、二つ以上の補助項目の一致、同じ位置と大きさを確認して統合します。既に追跡済みのフレームは一度だけ数え、その後の検出で区間を更新します。
- **高速ですれ違う3桁のプレート**。追加OCRを使う構成では、200 ms以内で同じ3桁を確認し、双方に独立した読みの裏づけと一致する補助項目がある場合も、速度と移動方向から追跡断片を照合します。
- **追加OCRの設定**。モデル設定の `numericVerifier` に補助モデルと対応する確度補正を指定すると、一連番号の通常の読みと補助OCRの一致、写り幅、複数フレームの支持から保存を判断します。補助モデルの桁別出力と連番出力が一致した場合も、通常の読みか、別に設定した桁ごとのモデルで同じ一連番号を確認します。数字の根拠が弱いフレームでも、既に確定した追跡へ枠を対応できれば検出区間を更新します。追加モデルを指定しない構成では既存の判定を使います。検出器の `sideRois` は中央に加えて左・右を交互に検出する設定、OCRの `fullOcrEvery` は地名などの詳細処理を行う間隔です。設定した間隔の途中も一連番号を読みます。
- **小さく写ったプレート**。設定した複数のOCRが別々のフレームで同じ一連番号を強く支持した場合に保存できます。検出スコアが低い枠で、独立した桁位置モデルと連番OCRが同じ別の一桁を支持した場合は保存を保留します。
- **検出範囲の追加**。`sideRois` は最大3領域を順に切り替えます。たとえば左、右、全幅を順に設定すると、各フレームの追加検出を1回に保ったまま全幅も定期的に確認できます。検出器の `fallbackRoi` に `[左, 上, 幅, 高さ]` を設定すると、検出スコア0.40以上かつ幅35 px以上（`minWidth` が大きい場合はその値以上）の枠がないフレームで、その領域を追加検出します。重なる枠は同じIoU条件でまとめ、採用候補の上限を適用します。
- **旧センサーとの互換性**。追跡情報を送らない旧センサーからの入力には、従来の一連番号と `mergeSeconds` による集約を適用します。追跡対応センサーの記録は追跡IDで識別します。
- **実行先**。検出器の前処理は ARM NEON の 1/2 整数縮小を使い、TFLite の検出・読取りモデルは実機で事前作成した OpenCL キャッシュを用いて Adreno GPU で処理します。PP-OCRv6 は Adreno 向けの重み 8 bit 圧縮 MNN モデル（固定幅 64・Batch=3、キャッシュ利用）と ONNX Runtime の INT8 CPU（可変幅・上限 128 ピクセル）を同時並列で実行します。キャッシュが無い場合や GPU・INT8 推論に失敗した場合は従来の CPU・浮動小数点経路へ自動で切り替えます。小さく写ったナンバーの読取り器（r4、PP-OCRv6 small）は幅128・256の固定幅TFLiteモデルをGPUで、それ以外の幅をONNXモデルでCPU実行します。使用中の実行先は「状態」タブの認識エンジン欄に表示されます。詳細は [ヘテロジニアス並列化と最適化の検証記録](plate-heterogeneous-acceleration-20261120.md) を参照してください。
- **取得間隔**。既定の目標は毎秒4フレームです。処理が時間内に終わらない場合は、完了後に純正カメラの最新フレームを取得します。
- **読み上げ**: 純正の発話機能は任意の文をクラウドで合成する方式で、他の車のナンバーが外部へ送られます。本体内でVOICEVOXを動かす方式は、合成に再生時間の約8倍かかりました。このため、条件の保存時にVOICEVOX APIで音声を作り、検知時は保存済みの音声を再生する方式にしています。

モデルの学習データ・精度の内訳・ライセンスは [モデルの説明](../models/plate/README.md)、学習と評価の手順は [開発・検証](development.md#ナンバー認識) を参照してください。

## 負荷と保存容量

認識サービスの取得目標は既定で毎秒4フレームです。次の取得までの待ち時間には処理時間も含みます。処理が間隔を超えた場合は次の最新フレームに移ります。CPUは最大1.5コア相当、メモリは384 MiBまでに制限しています。測定条件と読取り処理ごとの時間は [OCR処理時間の検証記録](plate-ocr-latency-20261120.md) を参照してください。

| 設定 | 初期値 |
| --- | --- |
| 記録の保存日数 | 365日 |
| 画像の保存容量 | 256MB（超えたら古い画像から削除） |
| 同じ車とみなす間隔 | 30秒 |
| 記録する信頼度の下限 | 0.6 |
| 記録に必要な検出回数 | 2回 |
| 1回で記録する信頼度 | 0.75（追跡時の下限は幅50px以上で0.75、45〜49pxで0.80。1で無効） |
| 地名・分類番号・かなの最小幅 (`fieldMinWidth`) | 70px（1〜1920） |
| 地名・分類番号・かなの一致割合 (`fieldMinShare`) | 2/3（0.5〜1）。幅を満たす異なる2フレーム以上で一致し、同数首位は空欄 |

## モデルとエンジン

学習済みモデルは `numbershare-reader-v7-lowres-v6s` で、`ppocrv6s_r4_rec.onnx` と `ppocrv6s_r4_w128.tflite` / `ppocrv6s_r4_w256.tflite` を使用します。モデルは [`models/plate/`](../models/plate/)、推論エンジンのビルド済みバイナリは [`prebuilt/plate-engine/`](../prebuilt/plate-engine/) にあり、通常のビルドと導入でそのまま本体へ入ります。学習・変換の手順とチェックポイントの入手方法は [開発・検証](development.md#ナンバー認識) を参照してください。
