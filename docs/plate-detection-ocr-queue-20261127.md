# 枠検出とOCRキューの分離（2026-11-27）

## 変更

ナンバープレートの枠検出・追跡とOCRを分離した。取得ループは検出枠を直ちに追跡へ渡し、OCRは同じエンジンプロセス内の専用スレッドで処理する。実機のキュー容量は2で、満杯時は古い未処理フレームを破棄して最新フレームを優先する。

OCR結果には元のフレーム番号と枠を含め、完了後に該当する追跡へ証拠を追加する。遅延結果によって検出フレーム数や移動量を二重に加算しない。未完了OCRがある追跡と元画像は完了または明示的な破棄まで保持する。モデルと推論エンジンは二重起動しない。

状態APIと1分単位のヘルスログへ、OCRキュー待ち数、完了数、破棄数を追加した。

## 検証

- フロントエンド本番ビルド、Go全パッケージのテストとvet、arm64ビルド、配布物生成に合格した。
- postboot単体テスト178件に合格した。
- ホスト上の実フレーム入力で、検出応答がOCR結果を待たずに返り、OCR結果が1〜2フレーム遅れて元フレーム番号付きで返ることを確認した。
- 実機へWeb/API本体、認識ワーカー、認識エンジンを導入した。永続ファイルと実行中コピーのSHA-256は一致した。本体は `3207449a88e04398ae8a34af53e9c81c42b2911bdff76c8692630ded534ddc80`、認識エンジンは `d39727f1d35a55acdcf54b31a2c539f62d33f88b1e31143c4a4e21da5dbc0f13` だった。
- 実機の目標8 fpsに対し、連続4回の状態取得で7.934〜7.935 fpsだった。OCR完了数は405から432へ増加し、キュー待ちは0〜1、破棄は0だった。認識サービスの再起動回数は0、メモリー使用量は約286 MiBだった。
- 前方・車内JPEG、SD録画の範囲読取とパストラバーサル防止に合格した。純正Communication、DriveRec、ImageRecog、Voice、QMMFはすべて `active/running`、再起動0を維持した。

GPSとWi-Fiは今回の机上検証では状態不明のままであり、成功扱いにしていない。Windows側のWi-Fi設定は変更していない。
