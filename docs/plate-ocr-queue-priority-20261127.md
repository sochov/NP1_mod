# OCRキュー優先制御と高速断片統合（2026-11-27）

## 目的

枠検出・位置追跡をOCR完了待ちにせず継続しながら、限られたOCRキューを次の順で使う。

1. OCRが一度も完了していない新規車両
2. 同一車両の過去最高画像より明らかに鮮明な画像
3. 番号・地名・分類番号・かなのいずれかが未確定な車両の低頻度再読

番号・地名・分類番号・かながすべて確定した後は、画像品質が大幅に改善した場合だけ再OCRする。

## 実装

- 検出枠をIoUと正規化中心距離で軽量に対応付け、3秒間の投入用トラックを保持する。これは登録結果を決める本来のGo側トラッカーとは独立した、キュー制御専用の補助情報である。
- 鮮明度はNV12のY面を最大およそ24行×24列で間引き、水平・垂直の2次差分と枠面積から算出する。追加モデルは実行しない。
- 同じ非空文字列を2回得た項目を投入制御上の「確定」とする。実際の登録可否・文字列合意は従来どおりGo側の複数証拠判定が行う。
- 未確定中は、過去最高から12%以上かつ0.75以上の品質向上、または最後の投入から850 ms経過した場合に候補とする。
- 全4項目確定後は、過去最高から30%以上かつ1.50以上の品質向上だけを候補とする。
- 実行中または待機中に同じ車両の画像がある場合、15%以上鮮明でなければフレームコピー前に抑制する。
- 待機キューが満杯の場合、新規車両・鮮明画像は低優先ジョブを置換できる。低優先再読は高優先ジョブを押し出さない。ワーカーも優先度の高いジョブから処理する。
- 抑制件数を `ocrSuppressed` としてセンサ状態および1分ごとのhealthログへ追加した。

## 高速横移動時の重複統合

実走行中の `86-92` で、約125 msごとに枠が横移動し、位置トラッカーが複数の1フレームIDを作る事象を確認した。従来の登録時統合は長時間追跡同士を前提にしていたため、この断片を統合できなかった。

短時間断片について、同じ3〜4桁番号、600 ms以内、地名・分類・かなに矛盾なし、枠の幅・高さが近い、行位置と移動量が物理的に連続可能、かつ少なくとも片方が2回以下・500 ms以下、をすべて満たす場合だけ同一encounterへ登録する。同時刻に存在する同番号や別の行・不可能な位置ジャンプは統合しない。

旧プロセスが当日書いた未統合断片は、次回の登録ストア初期化時に同じ厳格条件で明示的な `encounterId` を追記する。元レコードは追記型journalに残るため復旧可能である。
