# 小さく写ったナンバーの読取り改善と高速化（評価まとめ）

対象は NP1 本体（QCS610）のナンバー認識エンジン（`plate-engine`）とモデル一式 `numbershare-reader-v5-lowres-gpu` です。比較相手は2つあります。

- 現在の `main`：#12（PP-OCRv6 の INT8 化、MNN の GPU 実行、TFLite GPU の検出器・読取り器）を取り込んだ構成（エンジン `37706d70`）。下の「上流 #12 取り込み後」で比べています。
- #12 より前の `main`：エンジン `5a822b5d`、モデル `numbershare-reader-v4-night-context`（以下「v6」）。「結論」以降はこちらとの比較です。

## 上流 #12 取り込み後（現在の main との比較）

このブランチは #12 の上に載せ直しています。現在の `main` の機能（INT8 PP-OCRv6、MNN の GPU 実行、TFLite GPU の検出器・読取り器、OpenCL キャッシュ）はすべて残しています。

- 現在の `main` の設定（`plate-model.json`）で動かした場合、新しいエンジンの応答は #12 のエンジンと一致しました。開発分割の 120px と 70px で 60 枚ずつ、計 120 件すべてが同じでした。
- 一連番号の確認には、#12 の INT8 PP-OCRv6 を使います（`numberModel.fastFile`）。

開発分割で、両方の構成を実機で比べました。CPU 150%・メモリ 384MB の制限をかけ、OpenCL キャッシュは構成ごとに作成しています。テスト分割は取り込み前の最終比較で使ったため、ここでは使っていません。

**取り込み前（下の表）との違い**
- #12 には高速化のための処理があります。一連番号の信頼度が記録の下限（`--min-confidence`、既定 0.3）を下回るナンバーは、地名・かな・分類を読まずに返します。
  - 小さい幅ほど該当するナンバーが増えるので、全ナンバーで数えた地名の正答率は、取り込み前より低く出ます。
  - 記録の対象になるナンバーだけで比べると、120px は取り込み前と同じです（.72）。55px は .46 から .38 に下がっています。
- 一連番号の確認モデルも変わっています。取り込み前は float の PP-OCRv6、取り込み後は INT8 です。この違いが 55px での差にどれだけ効いているかは、確認できていません。
  - float の PP-OCRv6 を使う構成はエンジンの RSS が約 330MB になり、端末の空きメモリが少ないときに完走できませんでした。
- GPU が原因ではないことは確認しました。70px の 100 枚で、GPU を使わない場合も地名の正答率は同じでした。

## 走行映像での評価（評価キット 2026-11-14）

学習に使っていない走行映像の評価キット（3データセット、20,314 フレーム、目視で正しいと確認できた車 164 台）でも確かめました。このキットは一連番号だけを採点します。
- エンジンは aarch64 版を、Mac 上の arm64 Linux コンテナで CPU 実行しました。実機では CPU と GPU の読みがほぼ同じでした。
- 一連番号と信頼度は、現在の `main` と新構成で全フレーム一致しました。番号の読みはこの変更で変わりません。

**現在の `main` にもある精度の変化**
- 現在の `main` は、11/14 に採用した v6b より記録の正答率が低くなっています（94.1% → 86.1%）。特に夜間の np1 と camB で誤記録が増えています。新構成も数字は同じなので、この変更によるものではありません。
- 検出器は v6b と同じで、一連番号を読む `ocr.tflite` が違います。`ocr.tflite` は bce9353 で差し替えられました。

## 結論（#12 より前の main との比較、テスト分割）

- **全項目で精度が上がり、処理は約2.5倍速くなりました。**
  - 改善幅が大きいのは、幅120px以下の小さく写ったナンバーです。
  - 一連番号の精度は v6 と同じです。
- 評価は、学習にもパラメータ調整にも使っていないテスト分割で行いました。CPU使用量は150%まで、メモリは384MBまでに制限しています（本体サービスと同じ条件）。

## 何を変えたか

| 変更 | 内容 | 主な効果 |
| --- | --- | --- |
| 1. 文字認識モデル | PP-OCRv5 mobile（Apache-2.0）を追加学習（`ppocrv5_r2_rec.onnx`）。小さく写った状態（幅45〜130px）を再現した実写の切り出しを使い、元解像度の読みに合わせるよう学習。出力は日本のナンバーで使う273文字に限定 | 地名・かな |
| 2. 読み方 | 上段全体を読んで地名と分類番号を照合する（`topRow`）、双線形補間で切り出す（`sampling`）、かなを読む領域を見直す（`kanaRects`） | 地名・分類 |
| 3. 固定幅パディング | 切り出しの右側を埋めて幅128/256/384にそろえる（`padWidths`）。PP-OCRの学習時の入力形式に近づける | 分類・かな（+10ポイント前後） |
| 4. GPU実行 | 幅128と256の文字認識をOpenCL GPUで実行する（`gpu`、TFLite GPUデリゲート）。GPUが使えない場合はCPUで実行 | 速度 |
| 5. 一連番号の確認 | 一連番号の確認にだけ従来の PP-OCRv6 を使う（`numberModel`） | 一連番号を v6 と同等に維持 |

各設定は省略可能で、省略した場合は従来どおり動きます（[development.md](development.md) の「textOcr設定」）。

## 途中経過（開発分割）

数値は完全一致（70px）、ナンバーの採用基準は信頼度0.6以上、処理時間は1フレームの平均です。

| 構成 | 完全一致（70px） | 処理時間 |
| --- | --- | --- |
| v6 | .11〜.16 | 約1100ms |
| v5（追加学習なし）＋上段・かな改善 | .43 | 約330ms |
| 追加学習したモデル | .49 | 約330ms |
| ＋一連番号の確認に PP-OCRv6 | .49（一連番号 .78→.84） | 約455ms |
| ＋固定幅パディング（CPU） | .61 | 約560ms |
| **＋GPU（幅128・256）＝採用** | **.61** | **約440ms** |

試したが採用しなかったもの：
- int8/fp16 への量子化：精度が下がった。
- 超解像などの前処理：小さく写った状態の学習のほうが効果が大きかった。
- 一連番号の行を追加学習：一連番号は良くならず、他の項目が下がった。
- 一連番号の確認の閾値調整：効果がほぼなかった。
- v6 も GPU で動かす：メモリ不足で起動時に強制終了された。

## 評価の方法

- 評価データ（field-eval-web-v1）は、Roboflow Universe の公開データセット「Number Plate in Japan」v10（CC BY 4.0）の写真から作ったナンバーの切り出し 1,368 件です。ナンバーが写っているため、リポジトリには入れていません。
  - ラベルは、Lipla と VLM の読みが一致した項目だけです（人手による確認ではありません）。
  - 車（地名・分類・かな・一連番号の組み合わせ）単位で、開発分割 578 件とテスト分割 790 件に分けています。
  - 学習データ（所有者の写真・ドラレコの切り出しと合成画像）とは別の画像です。同じ車は 0 件、ほぼ同じ画像（縮小画像の相関 0.9 以上）も 0 件でした。一連番号だけが一致するものは開発分割に 52 件、テスト分割に 79 件あり、偶然の一致の範囲と考えています。
- 各ナンバーを、幅が 120/90/70/55px になるよう縮小しました。縮小には面積平均、軽いぼかし、センサー雑音を加えています。
- 縮小したナンバーを、1920×1080の灰色フレームにある検出範囲の中央に置き、NV12形式でエンジンの標準入力へ送りました。実機上で検出から読取りまでを通しで実行しています。
- 実機は NP1（QCS610、Adreno 612）です。`systemd-run -p CPUQuota=150% -p MemoryLimit=384M` の下で、サービスと同じ条件で計測しました。
- テスト分割は最終比較に1回だけ使いました。調整には開発分割だけを使っています。

## GPU 実行について

- 端末の `/usr/lib/libOpenCL.so`（OpenCL 2.0、Adreno 612）を実行時に読み込みます。
- 単体での速度比較です（CPUはXNNPACK 2スレッド）。

| 入力幅 | CPU | GPU |
| --- | --- | --- |
| 64 | 11.6ms | 11.7ms |
| 128 | 26.9ms | 17.7ms |
| 256 | 約55ms | 約33ms |

- GPU 化の準備としてモデルを書き換えています。どちらも計算結果は同じで、ONNXとの差は1e-5程度です（`tools/plate/gpu/`）。
  - HardSigmoid を `Clip(0,6)/6` に書き換えた。
  - 注意機構の5次元演算を4次元に書き換えた。
- GPU の精度は fp16（`precisionLossAllowed`）です。開発分割全体で CPU と同じ精度でした。
- GPU を1つの幅に使うごとに、メモリが約25〜30MB増えます。幅384は CPU で実行し、メモリの増加を抑えています。

## 制約・注意

- 地名・分類・かなの評価は、写真から合成したフレームによるものです。走行映像では、一連番号の読みが現在の `main` と同じことだけを確かめています（下の「走行映像での評価」）。
  - 2026-11-15・17 の NP1 走行映像（評価専用）の正解付けを進めています。
- 評価中に、端末がハードリセットしたことが1回ありました（GPU キャッシュの作成中、端末の負荷が高い状態）。原因は特定できていません。#12 の文書にも、GPU を使った計測中の原因不明の再起動が記録されています。
- 端末の空きメモリは、本体の他の処理によって 170MB〜1.4GB の範囲で変動しました。
  - サービスのメモリ上限（384MB）の範囲内には収まっています。
  - 評価中に端末全体のメモリが不足したとき、他のサービスがカーネルに強制終了された（自動で再起動）ことがありました。
- かなの誤読率は、55px で .12 でした（v6 は .11）。
- 学習スクリプトとデータは個人のナンバーを含むため同梱していません。追加学習済みの重みと、GPU 用モデルへの変換スクリプトだけを同梱しています。
