# Android Auto 投影

NP1をスマートフォンの代わりにして、ヘッドユニット（ナビ）の画面にAndroidアプリの横画面ダッシュボード（左に地図、右に前方カメラとナンバー一覧）を表示します。NP1には画面がないため、本体で画面を描画し、ハードウェアエンコーダーでH.264に変換して、Android Autoのプロトコルでヘッドユニットへ送ります。

設定は「システム → Android Auto」で行います。初期状態はオフです。

## 使い方（ヘッドユニットアプリ）

対応しているのは、ネットワーク上のスマートフォンを探して接続する方式（Headunit Server方式）のヘッドユニットアプリです。Open Headunit 4.1.0-beta2 で表示まで確認しています。

1. 「システム → Android Auto」で「Android Autoの投影を有効にする」をオンにして保存します。
2. ヘッドユニットをNP1のホットスポットへ接続します。SSIDとパスワードは「Wi-Fi / AP」画面で確認できます。2回目以降はヘッドユニット側が自動で接続します。
3. ヘッドユニットアプリの接続方式を「Headunit Server」（自動検索）にします。アプリはゲートウェイのNP1（`192.168.226.1:5277`）を見つけて接続します。
4. 画面の状態が「投影中」になり、ヘッドユニットにダッシュボードが表示されます。

同時に投影できるヘッドユニットは1台です。待ち受けはホットスポット（`nccap0`）とこの本体のループバック（adb転送）だけに開き、ファイアウォールでもホットスポットのTCP 5277だけを許可します。

## 画面

Androidアプリの横画面ダッシュボードと同じ構成です。

| 領域 | 内容 |
| --- | --- |
| 地図（左） | Web UIと同じOpenFreeMap（OpenStreetMapのデータ）のベクタータイルを本体で描画し、配色もWeb UIのミスト（ライト）・ナイト（ダーク）に合わせます。現在地（測位できないときは最後の位置を灰色。測位の注意は左下に表示）、過去24時間の走行経路、ナンバーの検出地点（通常は青、条件一致は大きい橙、推定位置は薄く）を重ねます。地名・道路名・施設名はラベルが重ならないよう地図全体で配置します |
| 信号（地図の左上） | 高度化PICSが有効なとき、Web UIのダッシュボードと同じく灯色と「青まであとN秒」（目安）・「青」・「青点滅」・「赤・残り時間不明」を表示します。0.4秒ごとに取得し、受信が途絶えて有効期限を過ぎると消します。方向の絞り込みがオンなら該当する灯器だけを表示します |
| ナンバーの通知（地図の右上） | 条件に一致するナンバー（NumberShareの危険登録を含む）を新たに検知すると、Android版と同じく見出し・時刻・大きいナンバー板・条件名・切り抜き画像のカードを8秒間表示します。起動時に既にある記録では表示しません |
| 前方カメラ（右上） | 純正の前方カメラ出力（NV12、約10fps）を縮小。高さは表示領域の半分までとし、超える分は上下を切り取ります。録画中とナンバー認識の状態を左上に重ねます |
| ナンバー一覧（右下） | 昨日と今日の記録を新しい順に、ナンバー板・検出画像から切り抜いたナンバー・時刻・経過時間・精度・検出回数で表示。条件一致はWeb UIと同じく淡い橙の背景・左端の橙の帯・ナンバー板の光彩で強調し、条件名を表示します。NumberShareの危険登録は赤。新しい検知は4秒間強調します |

画面の色は、自動（現在地の日の出・日の入り）、ライト、ダークから選べます。

本体での読み上げとLEDの通知（PICS・ナンバー）は従来どおり動作します。Android Autoの音声チャネルは使わないため、ナビのスピーカーからは鳴りません。

ヘッドユニットの画面が標準の比率でない場合（1600×600など）も、形を合わせて表示します。ヘッドユニットは標準解像度の映像を受け取り、画面の形を「余白」または「画素の縦横比」で知らせます。余白のときはその内側に配置し、画素の縦横比のとき（例: 1280×720を1600×600に引き伸ばす場合は1.5）は、画面上で正しい比率になる論理サイズ（この例では1280×480）で描いてから映像サイズへ引き伸ばして送ります。描画は論理サイズで行うので、処理は増えません。Open Headunitで1600×600（画素の縦横比1.5）と1280×720の両方を確認しました。

表示内容はNP1CCのWeb API（`/api/v1` の現在地・経路・ナンバー記録と検出画像・状態）から読み取ります。地図タイルはOpenFreeMapから取得し（Web UIと同じ）、地図の右下に出典を表示します。投影サービスはナンバーの記録やGPS履歴を直接読みません。

## 設定

| 項目 | 説明 |
| --- | --- |
| 最大解像度 | ヘッドユニットが提示する解像度のうち、この上限以下で最大のものを使います（800×480 / 1280×720 / 1920×1080） |
| フレームレート上限 | 10〜30fps。カメラ出力が約10fpsのため、変化のない間は送信を間引き、最低でも0.5秒ごとに1枚送ります |
| ビットレート | 800×480での値。大きい解像度では面積に比例して増やします |
| 地図の縮尺 | 広域〜詳細 |

設定は `state/androidauto/settings.json`（NP1CCが保存）にあり、投影サービスが2秒ごと、または保存時の通知で読み直します。

## 構成

| 要素 | 役割 |
| --- | --- |
| `np1-control-android-auto.service` | 独立サービス（`ncc --mode android-auto`）。NP1CCのWebプロセスとは別に動作し、CPU 80%・メモリ192MBに制限 |
| 描画 | Goで直接NV12へ描画。地図と一覧は内容が変わったときだけ描き直し、カメラは必要な行だけ読み出して縮小します |
| 符号化 | 純正の録画と同じGStreamer OpenMAX経路（`omxh264enc`）を子プロセスで使用。H.264 Baseline、IDRは2秒ごと |
| プロトコル | Android Autoのスマートフォン側（フレーム、TLS、サービス検出、映像チャネル、ACKによる送信制御、タッチ受信）を独自実装 |
| 状態 | `/run/np1-control-android-auto/aa.sock`。Webの「システム → Android Auto」に中継 |
| 保存先 | `/overlay/owner-apps/np1-control/androidauto`（証明書、地図のベクタータイルのキャッシュ最大32MB） |

プロトコルは公開されているヘッドユニット実装（DiAuto、AGPL-3.0）のメッセージ定義を参照して書き起こしました。DiAutoのコードは複製していません。日本語表示用にBIZ UDPゴシック（SIL OFL 1.1）を、表示する文字（UI、地名、かな、JIS第1水準漢字）に絞って同梱しています。

## 実機での確認（2026-11-26）

| 項目 | 結果 |
| --- | --- |
| ヘッドユニットアプリ | Open Headunit 4.1.0-beta2（Androidエミュレーター、ホットスポットの代わりにadb転送で接続）でTLS、サービス検出、映像チャネルが成立し、800×480の映像を8〜9fps、欠落なしで表示 |
| 接続から最初の映像 | 0.35〜0.64秒（PCの模擬ヘッドユニット） |
| 送信 | 約9fps、0.84〜0.95Mbps（800×480、ビットレート設定2.5Mbps） |
| CPU（1コア換算） | 投影サービス 約10.5%、エンコーダー 約5.2%（800×480、最適化後） |
| メモリ | 投影サービス 約30MB、エンコーダー 約11MB |
| ハードウェアエンコーダー | 純正の3系統（前方1080p/27fps×2、車内720p/16fps）の稼働中に、4系統目として800×480・1280×720・1920×1080の符号化に成功 |
| 純正録画への影響 | 投影中に記録された前方録画は180秒で4860フレーム（27fps）で欠落なし |

符号化を終えるときは入力を閉じて正常終了させます。強制終了するとビデオドライバーがセッション停止に失敗したログを残すため、サービスの停止も主プロセスだけに通知（`KillMode=mixed`）して子プロセスを正常終了させます。

## 車内カメラについて

当初は車内カメラを止めてエンコーダーの容量を投影に回す予定でしたが、上の実測のとおり車内カメラを動かしたままでも余裕があり、純正録画も欠落しませんでした。既存の「車内録画オフ」は録画開始を抑止して出力を捨てる方式で、車内のエンコーダー自体は止まりません。エンコーダーまで止めるには純正DriveRec内のパイプラインを停止・再開する必要があり、以前に負荷暴走と再起動を招いた方式に近いため、今回は実装していません。

## 純正ナビ（市販ヘッドユニット）の無線Android Auto

市販ナビの無線Android Autoは次の手順です。

1. スマートフォンとナビをBluetoothでペアリングする。
2. スマートフォンがナビのRFCOMMサービス（UUID `4de17a00-52cb-11e6-bdf4-0002a5d5c51b`）に接続し、ナビからWi-FiのSSID・パスワード・接続先（通常TCP 5288）を受け取る。
3. スマートフォンが**ナビのWi-Fi**に接続し、ナビへTCPで接続して投影を始める。

つまり標準の手順では、ナビがNP1のホットスポットに入るのではなく、NP1がナビのWi-Fiに入ります。RFCOMM上の手順（`WifiStartRequest`→`WifiInfoRequest`→`WifiInfoResponse`→`WifiStartResponse`・`WifiConnectStatus`）と、その後のTCP接続でのセッションは実装と試験を済ませています（`aap.PhoneWireless`）。

残っているのはBluetoothとWi-Fiの操作です。NP1のBluetoothは純正の`NEventWatcherCom`が独自スタックで管理しており、カーネルのBluetoothはありません。ただし純正のD-Busに次の機能が公開されていることを確認しました。

| D-Bus名 | 確認できた機能 |
| --- | --- |
| `SPF.EventBase.NPBTManagerHandler` | 機器探索（Inquiry）、発見可能化（Waiting）、ペアリング要求と確認応答、SDP検索、プロファイル接続、ローカル名とプロファイル設定 |
| `SPF.EventBase.NPBTSPPHandler` | SPP（RFCOMM）の送信とデータ・状態通知 |
| `SPF.EventBase.NWlanHandler` | Wi-Fi（STA）の接続・切断・検索 |

これらを介して、ナビとのペアリング、Android AutoのUUIDでのRFCOMM接続（BTを止めずに純正の枠表へUUIDを書く）、WPPでのWi-Fi情報の受信、リンクキーの保存と再設定まで実機で動作し、投影サービスに組み込みました（設定「登録済みのナビへBluetoothで接続する」と「ナビを登録」）。ナビのWi-Fiへの接続は未実装です。詳細は [Bluetooth経路の調査](android-auto-bluetooth-20261126.md) にまとめています。

また、市販ナビの多くはスマートフォン側の証明書がGoogleの発行したものかを検証しているとみられます（スマートフォン側を実装した [AACS](https://opensource.com/article/20/12/android-auto-open-source) は実車で証明書の有効期間に合わせて車の日付を変更する必要がありました）。本体で生成する自己署名証明書では市販ナビに拒否される可能性が高く、その場合は所有者が用意した証明書と鍵を `/overlay/owner-apps/np1-control/androidauto/cert/phone.crt`・`phone.key` に置いて投影サービスを再起動する必要があります。このリポジトリには第三者の証明書や鍵を含めません。

## 開発と検証

- 模擬ヘッドユニット: `go run ./cmd/aa-hu-sim -addr 127.0.0.1:5277 -out ../tmp/aa.h264`（`adb forward tcp:5277 tcp:5277` を併用）。受信したH.264はffprobe/ffmpegで確認できます。
- 単体試験: `go test ./internal/androidauto/...`。模擬ヘッドユニットとの往復（TLS、断片化、送信制御、タッチ）、無線手順、描画、エンコーダー引数を確認します。`AA_PREVIEW_DIR` を指定すると、架空のデータで描いた画面をPNGで保存します（地図タイルを取得します）。
- 本体での一時実行: 設定ファイルの`stateDir`と`NCC_AA_DATA_DIR`を一時ディレクトリにすると、導入済みのサービスに触れずに試せます。`NCC_AA_PPROF=127.0.0.1:6061` でプロファイルを取得できます。
- フォントの更新: `python tools/androidauto-font-subset.py --source <BIZ UDPゴシックのttfとOFL.txtのディレクトリ>`。表示する文言を増やしたときは再生成します。
