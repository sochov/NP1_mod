# NumberShare v7 / low-resolution v6s（numbershare-reader-v7-lowres-v6s）

PP-OCRv6 small を追加学習した `ppocrv6s_r4_rec.onnx` と、同じ重みのGPU用 `ppocrv6s_r4_w128.tflite` / `ppocrv6s_r4_w256.tflite` を使います。273文字のCTC出力と辞書 `ppocrv5_r2-dictionary.json` は従来と共通です。一連番号の読取り器は plate-v2 で、PP-OCRv6 INT8で照合します。

学習には、車両グループ・地名・かなで重みを調整した実写の切り出し、描画した合成画像、架空の文字で生成した写実的な合成画像とその撮影条件違いの編集画像を使いました。生成・編集画像は、VLMで全項目を読み戻せたものだけを使っています。約34px未満では読取りを控える学習を行いました。QCS610実機を含む評価条件と結果は [評価まとめ](../../docs/plate-lowres-evaluation.md) を参照してください。

# NumberShare 0.8.1 / night context

PP-OCRv6 + NP1由来の数字・かな・分類番号モデル。全処理は端末内。
地名が未読のとき、分類番号を含む上段を2領域で再照合し、文字が欠ける場合は上段の高さを広げる。
地名の各文字の元確率・語全体のスコア・分類番号の完全一致を確認。
かなが未読のときは下段全体を2領域で読み、既に読めた一連番号と完全に一致する場合のみ補完。
補助の地名モデル入力には5/95パーセンタイル、最大4倍の明暗正規化を使用。複数の元CTC領域と一致し、強い反対候補がないことを要求する。
独立2カメラフレームの完全ナンバー一致後のみ保存する。

0.7.1との小規模な開発比較:
- 実際の夜間写真4点の6切出しで、正しい地名採用2→4。全項目GTの3例で完全採用2→3。
- 昼間の公開開発例の完全GT39例で28→30、別写真19例で4→7、車載切出し3例で3→3。
- 確認済み項目の誤採用はこの比較で増加なし。夜間の看板・ロゴ10例で完全ナンバーの誤採用0。
- 低照度シミュレーションは実際の夜間映像とは区別する。

かな専用モデルの夜間風追加学習2000更新、日本語専用OCR、CLAHE/二値化も比較した。
追加重みは今回の端末処理へ採用していない。採用したのは文字行の再照合と補助入力処理。
Java本番OCR/YUV/CTCは同じ版のPC用ONNX Runtimeで23入力を照合。今回のPixel実機・実走行は未検証。
モデル・ライセンスはmodel-manifest.jsonとLICENSING.md、夜間の比較はnight-evaluation.jsonを参照。
夜間写真は評価用。利用者の画像・動画は保存・送信しない。

0.8.1: カメラ画像のDataSpaceを参照し、フルレンジJFIFと限定レンジを区別して明暗・RGB変換する。Pixel 9aの解析入力は3840×2160、DataSpace 0x08c20000。従来の限定レンジ固定変換で失われていた暗部・明部の階調を保持する。

## NumberShare v8 / 限定アンサンブル

通常の一連番号OCRには `ocr.tflite` と `numeric-verifier.tflite` を使います。幅35〜64 pxの4桁プレートで主OCRと検証器が競合した場合だけ `ocr-legacy.tflite` を追加実行します。旧モデル単独の値は採用せず、主OCR、数値検証器、桁位置OCR、系列候補の一致または桁別多数決を確認します。固定182台の再生では147台（80.8%）を正読登録し、誤読登録は0台でした。
